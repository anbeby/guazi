# 瓜子平台后续升级标准流程

生效时间：2026-10-15。适用业务服务器：`192.168.3.5`，执行用户 `zhaopeng`。

**唯一正式发布入口**：`/home/zhaopeng/guazi/deploy/scripts/release-guazi.py`。旧的 `release-v11-production.sh`、`release-v11-guardfix-web.sh` 只保留作历史记录及对应检查点回滚，不用于新版本发布。新发布统一使用现有 Compose 项目 `guazi`，入口固定 `127.0.0.1:18083`。增值运营平台 `18080`、公网 DNS/Nginx/证书不在本流程的修改范围。

## 1. 每次发布前准备

1. 在隔离环境完成该版本构建、类型检查、API 测试、页面与业务验证。若有迁移，先用正式库备份恢复到**独立测试库**，在新 API 镜像上演练升级、检查目标修订；同时验证回退或备份恢复方案。不要直接用正式库试迁移。
2. 生成带版本号的 `gz-api:<版本>`、`gz-admin-web:<版本>` 镜像，记录镜像 ID 和发布包 SHA256；将镜像加载到业务服务器。不要覆盖 `latest` 或删除旧镜像。
3. 在 `deploy/release-plans/` 新建一个 JSON 发布计划。参考 `v1.1-current-check-20261015.json`，填写**现网镜像**、**目标镜像**、**现网 Alembic 修订**和**目标修订**。`release_id` 每次唯一。API 与 worker 使用同一镜像。
4. 发布计划只能改 API、worker、前端镜像及经演练的 Alembic 版本。如需改端口、数据卷、网络、服务名、配置或架构，先单独评审，不夹带在镜像升级中。

计划示例（版本号仅作格式说明，不可直接执行）：

```json
{
  "release_id": "v1.2-example",
  "base_images": {
    "api": "gz-api:v1.1-rc1",
    "worker": "gz-api:v1.1-rc1",
    "admin-web": "gz-admin-web:v1.1-guardfix-20261014"
  },
  "target_images": {
    "api": "gz-api:v1.2-example",
    "worker": "gz-api:v1.2-example",
    "admin-web": "gz-admin-web:v1.2-example"
  },
  "db_from": "0003_open_lead_portal",
  "db_to": "目标修订号"
}
```

无数据库迁移时，`db_to` 与 `db_from` 填相同修订号。当前 `v1.1-current-check-20261015.json` 是**预检样本**，目标镜像等于现网镜像，工具会拒绝拿它执行发布。

## 2. 预检，不切换服务

在业务服务器执行：

```bash
cd /home/zhaopeng/guazi/deploy
python3 -B scripts/release-guazi.py check release-plans/<发布计划>.json
```

预检会从现用 `docker-compose.production-v1.yml` 生成 `docker-compose.candidate-<release_id>.yml`，只替换三处镜像引用，再执行 Compose 配置检查。它还核对：

- `/data/guazi` 属于 `/data` 数据盘且至少剩余 5 GiB；
- `.env` 项目名严格为 `guazi`，现有容器都带 `guazi` Compose 标签；
- 瓜子网关仍绑定 `127.0.0.1:18083`，增值运营网关仍绑定 `127.0.0.1:18080` 且健康；
- 正式库修订、现用镜像标签及容器镜像 ID 与计划一致；
- 目标镜像已加载、为 amd64，目标迁移修订存在于目标 API 镜像；
- 当前 API、worker、前端、网关及数据服务健康，`/ready`、首页、登录、供应大厅、采购大厅为 HTTP 200。

**预检不通过就停止**。不要改项目名、换端口、手工删除旧容器或用 `docker-compose down` 绕过检查。修正发布计划或镜像后重新预检。

## 3. 正式切换

在确认构建与迁移演练已通过、备份空间足够后执行：

```bash
cd /home/zhaopeng/guazi/deploy
python3 -B scripts/release-guazi.py apply release-plans/<发布计划>.json --execute
```

脚本再次执行完整预检，然后自动按以下顺序处理，仅操作 `guazi`：

1. 在 `/data/guazi/backups/release-<release_id>-<时间>/` 保存旧 Compose、受限权限的 `.env`、原容器和镜像 ID、数据库版本；备份 `gz_platform`、`gz_odoo`、`superset`，对备份做 `pg_restore -l` 与 SHA256 校验，给旧镜像加 `pre-<release_id>` 标签。
2. 暂停瓜子 FRP 与网关，停 API、worker、前端写入；形成 `gz_platform-final.dump` 和 `uploads-final.tar`。增值运营平台不停止。
3. 如需迁移，用目标 API 镜像的一次性容器运行 Alembic，再核对目标修订。**迁移先于新版常驻 API 启动。**
4. 始终以 `docker-compose -p guazi` 和 `--force-recreate` 替换旧 API、worker、前端，待健康后启动瓜子网关；验收 18083 的 `/ready`、首页、登录、供应大厅、采购大厅。
5. 只有内部健康通过才提升候选 Compose 为正式文件，并按原状态恢复瓜子 FRP。公网 HTTP/HTTPS 是另外的验收门槛，脚本不会改公网配置，也不会把云入口 403 当作应用健康。

状态记录在检查点 `state.json`。成功为 `released`。执行前后记录检查点路径和容器镜像 ID。

## 4. 故障与回滚

- **停服务前失败**：现网保持原样，检查点记为 `failed-before-stop`。
- **未迁移数据库、切换中失败**：脚本恢复旧镜像标签与原 Compose，重建旧容器并验证健康，然后按原状态恢复 FRP，检查点记为 `rolled-back`。
- **迁移已经开始后失败**：立即停止瓜子 FRP、网关及应用，检查点记为 `manual-review-required`。不要自动降级或覆盖数据库；先比较现库与 `gz_platform-final.dump`、`uploads-final.tar`，确认是否产生新写入，再制定数据恢复和旧镜像回退步骤。这是防止丢失线索、订单和上传文件的硬边界。
- **已发布版本需要回滚且数据库修订未变**：可以执行以下命令；脚本确认运行镜像确属该检查点后恢复旧 Compose 和旧镜像。数据库保持现有数据。

```bash
python3 -B scripts/release-guazi.py rollback /data/guazi/backups/release-<release_id>-<时间> --execute
```

若数据库修订已改变，此命令会拒绝自动回滚。不得把 `alembic downgrade` 视为无损恢复。数据恢复应先在独立数据库验证备份，再安排停写切换。发生 `manual-review-required` 时优先保全当前数据库与备份，不运行 `down -v`、`docker system prune` 或覆盖原始检查点。

## 5. 每次发布结束的记录

记录计划文件、目标镜像 ID、构建测试结果、迁移演练结果、预检输出、备份检查点、`state.json` 状态、正式库修订、容器健康、五个内部 URL、FRP 状态和 18080 增值运营平台状态。公网 HTTP 测试与 HTTPS 正式入口分别记录；目前域名受云入口备案拦截时，不能写成公网已通过。

## 6. 2026-10-15 固化验证

预检样本在业务服务器通过：项目 `guazi`、端口 18083、数据库 `0003_open_lead_portal`、现网镜像和健康状态均吻合；目标 Alembic 修订可在镜像中找到。错误的旧镜像标签被预检拒绝。对当前版本执行 `apply` 被“无版本变化”防护拒绝，瓜子与增值运营平台容器 ID 未改变。**本次没有执行真实版本切换或数据库迁移。**
