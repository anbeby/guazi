# 第十师瓜子油料数字化交易平台 —— 总体技术架构

版本：v1.0（第一阶段）
编制：项目技术负责人

---

## 1. 建设背景与定位

第十师北屯市是新疆重要的瓜子油料（葵花籽、南瓜籽、打瓜籽）集散与加工基地。产业现状的痛点是：

- 交易靠电话/微信/线下撮合，**价格不透明、履约无凭证**；
- 园区（交易市场）档口、入驻企业、租金费用**台账化、纸质化**；
- 商户自身缺乏轻量 ERP，**进销存与账目靠 Excel**；
- 产业数据散落各处，**政府/园区无法掌握产业运行态势**；
- 农产品**质量安全溯源链条断裂**，检测报告无法随货流通。

因此平台定位不是"再建一个商城"，而是建设**产业互联网基础设施**：

```
产业互联网交易平台（撮合 + 履约 + 结算）
        +
智慧园区管理（园区 / 区域 / 档口 / 入驻 / 合同 / 费用 / 巡检）
        +
商户经营管理（轻量 ERP：商品 / 采购 / 销售 / 库存 / 应收应付）
        +
数据分析中心（产业驾驶舱 / 价格指数 / 跨库报表）
```

### 2.1 为什么是"双核心"而不是"单核心"

- **Odoo 不适合做的事**：面向 C/B 端的高并发标准化 API、产业域特有对象（园区档口、溯源批次、撮合询报价）、面向多租户的数据隔离策略、大屏聚合查询。Odoo 的 ORM 与视图体系是为"企业内部流程"设计的，做互联网交易前台会非常别扭，且二次开发耦合度极高、升级困难。
- **自研不适合做的事**：总账会计、多币种税务、采购到付款（P2B）、销售到收款（O2C）、MRP、工资社保。这些是 Odoo 十几年沉淀的强项，重造代价极高。

因此采用 **Odoo 做"企业经营管理底座" + 自研做"产业交易与运营"** 的双核心架构，两者通过 **企业主数据同步 + 单据同步** 打通，边界清晰、可独立演进。

## 3. 关键架构决策（ADR 摘要）

| 编号 | 决策 | 理由 | 代价与缓解 |
| --- | --- | --- | --- |
| ADR-01 | 采用 Odoo 17 CE 而非自研 ERP | 采购/销售/库存/财务/CRM 成熟，社区生态好，可私有化 | 需定制开发规范；通过 `gz_*` 模块隔离定制，禁止改核心代码 |
| ADR-02 | 自研平台独立进程 + 独立数据库 | 与 Odoo 解耦，可独立扩容与发布；避免污染 Odoo 事务 | 引入跨库一致性，用 outbox + 幂等 + 对账兜底 |
| ADR-03 | 同实例双库（gz_odoo / gz_platform） | 便于统一备份、统一 DBA 运维，又能逻辑隔离 | Superset 需配两个连接或使用 postgres_fdw |
| ADR-04 | 交易平台后端选 FastAPI + SQLAlchemy 2.0（同步会话） | 类型友好、自动 OpenAPI、生态成熟；同步模型易于保证事务一致性，团队上手快 | 高并发场景下可对聚合查询单独引入异步连接池（预留） |
| ADR-05 | 认证采用 JWT(HS256) + Redis 黑名单，密码采用 PBKDF2-SHA256 | 只用标准库实现，零第三方加密依赖，避免 passlib/bcrypt 版本兼容坑；PBKDF2-SHA256 迭代 26 万次满足等保要求 | 后续可平滑替换为 Argon2id |
| ADR-06 | ElasticSearch / MinIO / Redis 全部**可降级** | 中间件故障不应导致交易主链路不可用 | 封装 `search/storage/cache` 适配器，失败自动回退 SQL LIKE / 本地磁盘 / 进程内缓存 |
| ADR-07 | 电子结算**不自建支付**，只做交易流水与对账 | 合规要求：资金走银行/持牌机构；平台只做信息流与凭证 | 预留 `payment_record` 与银行回单导入接口 |
| ADR-08 | 前端 Vue3 + Vite，构建产物由 Nginx 托管 | 生态成熟、Element Plus 适配中后台；与 Odoo 前端解耦 | 需独立构建流水线 |
| ADR-09 | 全部 Docker 化，单机 compose 起步，K8s 平滑迁移 | 交付快、运维简单、环境一致 | compose 文件按"可拆 K8s"原则设计（无宿主绑定、配置外置） |

资源建议（生产最小集）：8 vCPU / 32 GB RAM / 500 GB SSD。
ElasticSearch 单独 4 GB 堆，Odoo 2 workers，API 4 workers。

## 6. 非功能性设计

| 维度 | 目标 | 实现手段 |
| --- | --- | --- |
| 性能 | 核心列表接口 P95 < 300ms | 组合索引、分页强制、Redis 缓存驾驶舱聚合 |
| 可用性 | 交易主链路不依赖 ES/MinIO/Redis | 适配器降级策略 |
| 一致性 | 订单确认与库存扣减强一致 | 单库事务 + `SELECT ... FOR UPDATE` 行锁 + 幂等键 |
| 安全 | 满足等保二级 | JWT、PBKDF2、RBAC、企业级数据隔离、操作审计日志、SQL 参数化 |
| 可观测 | 快速定位 | 结构化日志、`/health` `/ready`、请求耗时中间件 |
| 可扩展 | 新模块零改造接入 | 一级模块独立路由包 + 权限码注册表 |
| 数据合规 | 业务数据真实落库 | 所有接口直连 PostgreSQL，无 Mock 数据层 |

## 7. 阶段一交付验收口径

1. `docker compose up -d` 后 8 个服务全部 healthy；
2. `python -m app.initial_data` 可重复执行并生成完整种子数据；
3. `pytest` 全绿，覆盖认证、权限、商户、商品、库存、交易全链路；
4. 通过 OpenAPI 文档或内置控制台可完成"发布商品 → 询价 → 报价 → 下单 → 扣库存 → 生成流水与结算单"闭环；
5. Odoo 后台可见同步过来的商户、商品与订单单据。
