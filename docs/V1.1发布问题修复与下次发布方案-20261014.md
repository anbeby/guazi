## 下次发布顺序

在业务服务器 `/home/zhaopeng/guazi/deploy` 执行。发布脚本只管理 `guazi` 项目，不运行 `down -v`，不触碰其他项目。

```bash
bash scripts/release-v11-production.sh check
bash scripts/release-v11-production.sh apply --execute
```

`check` 必须先通过公网 HTTPS 检查。`apply` 执行：

1. 在 `/data/guazi/backups/v11-release-时间戳/` 保存正式 Compose、`.env`、旧镜像/容器 ID、正式 Alembic 版本，备份并校验 `gz_platform`、`gz_odoo`、`superset` 三库。
2. 停止瓜子网关和 API/worker/前端写入，再备份一次 `gz_platform`，形成最终一致的回滚点。
3. 以 **V1.1 镜像的一次性迁移容器** 执行 `alembic upgrade head`，确认 `0003_open_lead_portal`。常驻 V1.1 API 启动时会调用 `create_all`，因此不能让其先于迁移接触正式库。
4. 通过 `-p guazi --force-recreate` 替换旧 API、worker、前端容器；确认三者 healthy 后再启动瓜子网关。不会创建另一 Compose 项目或与旧容器抢同名。
5. 验证业务服务器本机 `/ready`，以及公网首页、登录页、供应大厅、采购大厅；成功后才将候选 Compose 晋升为正式 Compose。

切流前失败会自动停用新版、降回 `0001_initial`、恢复旧 Compose 与 `.env` 并重建旧容器。**公网流量打开后不能盲目降级或恢复旧数据库**：新线索、采购需求、收藏或已有记录修改可能丢失。此时脚本立即停止瓜子网关、保留数据和备份，标记 `manual-review-required`，先核对新增写入再决定数据回退。回滚检查点和状态均在上述备份目录。
